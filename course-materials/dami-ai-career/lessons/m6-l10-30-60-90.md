## Why a 30/60/90 plan?

Starting a new AI or data job is exciting and a little overwhelming. A **30/60/90 day plan** turns that fog into three clear phases: in your first 30 days you **learn**, by 60 days you **contribute**, and by 90 days you **own** a piece of work. Writing it down — even one page — shows your manager you are intentional, and gives you something to review in your one-on-ones.

You do not need to know everything on day one. You need a direction.

## Days 0-30: Learn and set up

The first month is about absorbing, not impressing. Get your access and environment working, read the code, explore the data, and meet people. Clone the main repo and get it running locally before anything else.

```bash
git clone https://github.com/your-org/main-service.git
cd main-service
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pytest -q                   # confirm the tests pass
```

Keep a running document of every question you ask and the answer you get. It captures gaps in the docs and helps the next new starter.

## Days 31-60: Contribute

Now start shipping small, safe wins: a bug fix, a test, a documentation update, or a tiny feature. Get it reviewed and follow the team's workflow exactly. This is also when you might write your first real code against your stack — for example, calling the model API the team uses.

```python
import os
from anthropic import Anthropic

client = Anthropic()   # reads ANTHROPIC_API_KEY from the environment

msg = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Summarise this ticket in one line."}],
)
print(msg.content[0].text)
```

Never hard-code secrets — keep your key in an environment variable like `ANTHROPIC_API_KEY`.

## Days 61-90: Own a piece

By now you should need less hand-holding. Take ownership of a feature, a dataset, or a small service end to end — design, build, test, ship, monitor. Ask for feedback explicitly: *what should I do more of, and what should I change?*

## Common mistakes to avoid

Don't try to rewrite everything in week one. Don't go silent when stuck for hours — ask after a sensible attempt. Don't skip the boring docs and onboarding meetings. And don't make risky production changes before you understand the tests and review process.
